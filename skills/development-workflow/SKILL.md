# Development workflow

One request uses one acceptance contract and a parent-owned workflow. Read the
target checkout's instructions and [effective policy](references/policy.md).
Choose from the actual target project before dispatch: existing `openspec/` means
OpenSpec; otherwise use a lightweight contract. Do not initialize OpenSpec merely
because a task was requested. Explicit user selection takes precedence.
Ordinary implementation/fix requests authorize the bounded configured managed
builder in a separate worktree and parent plan/code review, without requiring
"worktree" or repeating phase approvals. Explicit action/provider/delegation
restrictions and host permissions prevail; configuration alone starts nothing.
Questions/advice alone do not dispatch work. Architecture-only stops at reviewed
design. This instruction contract is not host runtime enforcement.

## Initiator

1. Classify the request, resolve scope/target ref and actual action limits.
   Negotiate host identity, isolation, visibility, harness/model/effort,
   observation/recovery and real human question/tool-approval channels through
   orchestration. Record supported/unsupported/unknown with evidence; withhold
   dependent dispatch on a required gap rather than silently replace a required
   builder with root implementation. Qualify actual worker checkout writes, atomic
   assigned-report writes, required checks and task-required network access using
   bounded harmless probes under existing authority, not configuration alone.
   Record capability evidence through [effective policy](references/policy.md);
   missing evidence is UNVERIFIED. No mandatory full access or new phase approval.
   Continue independent authorized work.
2. Before substantive design, discover the public host once through the
   Guild adapter bundled with orchestration. For an eligible original
   parent in capable Guild, use [native entry](references/native-entry.md): create
   only the nonempty draft note/matching OpenSpec skeleton needed for selection,
   register/show Process, then prepare the evolving contract in the original
   checkout. Start is not contract acceptance or worker/review permission. Native
   mode owns checkpoint/review/report/dispatch for this task; use that reference
   instead of the portable steps2-6 below; do not launch external review/manual workers. Preserve
   actual initiating identity and stable request/run receipts across retries.
   For capability absence select portable mode before Start; after native
   registration a gap never authorizes a second controller. Assigned sessions
   follow their existing assignment rather than register a nested run.
   On the portable route, prepare the contract first with spec-design, proportional
   to the task.
   Resolve material open questions and record the agreed UI target where affected
   before implementation; reuse settled decisions rather than adding phase
   approvals. Distinguish contract review acceptance from user product decisions.
   With existing OpenSpec, reuse/create one matching change, obtain schema
   instructions and validate the persisted artifacts. Without it, record scope,
   acceptance checks and a concise task plan in one existing project document or
   one small task note; skip OpenSpec CLI, schema, baseline/delta and archive steps.
   A small fix needs no separate design document or full brainstorming ceremony.
   Complex work still uses an independent managed designer. Record accessible
   artifact paths/revision/digests and format-appropriate preparation evidence.
   Verify those files before parent plan review through
   [installed revust](references/review.md); only matching accepted review
   evidence marks the contract accepted. The lightweight route preserves that
   review, managed implementation, code review and live acceptance requirements.
   With provider/worker dispatch prohibited, continue independently permitted
   preparation up to the first actual prohibited or unavailable operation.
   An existing OpenSpec directory with invalid/missing tooling is a setup gap,
   not permission to fall back silently. A route description is not a saved or
   accepted contract. Preserve pending checkpoints and remaining allowance.
3. Use orchestration to assign the bounded configured builder in its own
   worktree with complete task, exact available contract/revision, ownership,
   effective selections, resources, checks and authorized report path. Guild
   workers are visible; qualified non-Guild workers may be non-visible. Verify
   actual start/identities. Only the root dispatches; builders never delegate,
   independently review or steer sessions. The portable route needs no native registration; selected native mode
   retains its existing run instead of manual dispatch.
4. Stay active and supervise each assigned ID fairly through bounded host
   waits/events and durable results. A completed turn needs result inspection
   and its next authorized parent checkpoint, not a final response leaving
   workers running. Consume the report, reconcile its exact artifacts and record
   the checkpoint outcome, next action and owner in the current root receipt
   before continuation or turn end. Follow orchestration's supervision/recovery
   protocol and continue the same eligible idle/done session through corrections.
5. Inspect engineering-quality checks and acceptance-testing observations;
   parent alone reviews the exact implementation snapshot with revust within
   separate remaining plan/code round limits. Verify supported findings, continue corrections
   in that builder and invalidate affected stale evidence. Root integrates
   exact prerequisite/consumer revisions and observes combined final behavior.
6. Accept only supported final evidence, inspecting the builder's result against
   the agreed behavior and UI target. Unmet agreement remains unfinished work;
   omitted material choices need resolution; new requests update the same scope
   record. Report implementation, verification, ready-for-inspection and accepted
   status distinctly. A done turn, green checks or clean review alone do not mean
   task completion. Required absent review/live/integration
   gates remain UNVERIFIED. Record readiness and prepare concrete local branch
   and MR/PR text; no implicit push, publication, merge, cleanup or deployment.
   Keep pending pilot/global tasks open and the builder available.

## Assigned designer or builder

Do the accepted tasks in your assigned checkout, preserving unrelated work.
Designer uses spec-design; builder uses engineering-quality and acceptance-testing.
Verify the supplied contract/revision, ownership, dependencies and report path.
Before dependent work, qualify actual checkout and atomic assigned-report writes,
required checks and task-required network using bounded harmless probes under
existing authority. Report gaps as UNVERIFIED; configuration alone proves nothing,
and qualification requires neither blanket full access nor repeated phase approval.
Follow tasks to meaningful checks and required commits; report contradictions to
root before dependent work. Keep the same session for corrections, including
parent-owned review/evaluation checkpoints; do not attempt those launches yourself.

Publish the explicitly assigned atomic report using
a temporary sibling followed by atomic replacement, with exact paths,
head/digests, evidence, limitations and next action. A checkpoint is pending
parent work, not acceptance. Pause a dependent decision until the actual human
answer and a protected tool action until its real host approval. Do not answer
another session's permission prompt. Existing explicit authorization continues
through phases; timeouts and silence supply no approval or successful result.

## Methods and precedence

Use Superpowers as optional task-specific methods, not a mandatory sequence.
For an ambiguous substantial design, use brainstorming and planning; for a bug,
use diagnosis and meaningful regression checks; before completion, inspect actual
verification evidence. Small clear changes need no separate brainstorming session,
extra design file or second plan. Missing Superpowers is not a setup blocker;
apply the relevant engineering method directly. Existing project-specific test
and quality requirements still apply. Model names do not decide which checks to
skip. This workflow owns the selected contract, role/worker routing, persistent
corrections, parent review, accounting and phase continuity. Competing plans,
reviewer/subagent dispatch, repeated phase approvals and branch-publication menus
are superseded; do not edit plugin caches. User/host restrictions remain highest.

## Observable progress and scope control

Assignments and reports identify required scope, necessary compatibility and
optional additions, plus the concrete accepted UI target and first useful working
preview. Agent-added shells/platforms require a demonstrated dependency on the
requested behavior; otherwise defer them. Parent checkpoints stop drift while
preserving affected callers. An unmet original contract remains unfinished work;
a new request changes that contract explicitly.

Build and supervise small observable vertical checkpoints in the same task and
session. Report what works, its evidence, next visible outcome and actual blocker.
Before full code review require minimal real interaction: fill the actual empty
input, execute the action, observe output and verify persistence where relevant;
use the affected API/CLI/native equivalent. Preview/prototype is not acceptance.
Missing access remains UNVERIFIED; checkpoints add no automatic approval gate
and do not stop already authorized work. Before corrections, map changed behavior
and paths to invalidated/retained evidence, required reruns/re-review and final
reviewed identities using acceptance-testing. Preserve profile, exact scope,
history and round limits; do not apply prior clean review to an unreviewed snapshot.

Distinguish managed-worker assignments from user topic handoffs through
orchestration and its bundled handoff/state guidance. Before creating a topic
session, qualify the review/continuation owner and usable host-supported route.
If promotion is unsupported retain the eligible parent, without identity stripping,
manual human courier as default, or suggestions to skip required review.
